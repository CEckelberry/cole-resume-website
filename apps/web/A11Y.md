# Accessibility posture

This file documents the a11y design choices baked into the site and notes
work deferred to v2. The site was built with a11y in mind from the start
rather than retrofitted; the patterns are repeated across components.

## Built in

**Document structure**

- `<html lang="en">` set in `src/app.html`
- One `<h1>` per route; `<h2>` for sections; `<h3>` for cards. No skipped levels.
- Semantic landmarks: `<nav>`, `<main>`, `<article>`, `<section>`, `<footer>`, `<aside>`
- Skip-to-content link in `+layout.svelte`, visible on focus

**Keyboard + focus**

- Every interactive element reachable via tab in document order
- Visible focus ring on every interactive element: 2 px pink outline, 2 px offset
  (defined globally in `src/app.css` via `:where(...):focus-visible`)
- `:focus-visible` (not `:focus`) so mouse clicks don't show the ring,
  keyboard users always do

**Screen reader**

- Decorative SVGs (mesh, polygons, icons inside buttons, traffic-light dots)
  are `aria-hidden="true"`
- Icon-only buttons (theme toggle) have `aria-label`
- Project cards are anchor-wrapped with descriptive `aria-label` that
  includes the project's blurb so a list-by-link surface is informative
- Contact form: associated `<label for>`, `aria-invalid`, `aria-describedby`
  pointing at error messages, `role="status" aria-live="polite"` on the
  success state, `role="alert"` on the form error
- Terminal animation has a `role="img"` + `aria-label` reading out the
  command output as plain prose, since the visual reveal is decorative
- Hero name has `aria-label="Cole Eckelberry"` so screen readers don't
  read the visual layout split between two `<span>` elements

**Reduced motion**

- `prefers-reduced-motion: reduce` honored across:
  - Mesh-blob drift, polygon scroll-rotation
  - Stack marquee
  - Hero terminal typing animation (skips to final state)
  - Project-card hover lift
  - Page transitions (view-transition-old/new)
  - Pulsing status dots in the nav, footer, and case-study heroes
- Global last-resort fallback in `src/app.css` clamps every animation +
  transition to 0.01 ms when reduced motion is requested

**Color scheme**

- `prefers-color-scheme` honored on first paint via the inline script in
  `src/app.html`
- Light/dark toggle persists to `localStorage["mode"]`
- `color-scheme` CSS property propagated so native form controls match

**Color contrast (against the cotton-candy palette)**

- Body text in dark mode: white on `#0e0820` ≈ 18.7 : 1 (AAA)
- Body text in light mode: `#1a1322` on `#fefcf8` ≈ 16.4 : 1 (AAA)
- Tertiary text in light mode (`#888780`) hits ≈ 4.13 : 1 against the canvas;
  used at small-text sizes (eyebrows, microcopy) where 3 : 1 is acceptable
  for non-essential UI; primary text-secondary remains > 4.5 : 1
- Accent colors (pink, teal, purple, amber) are used either
  - as decorative fills/backgrounds, or
  - as text at heading sizes (≥ 24 px) where the 3 : 1 large-text floor applies

**Forms**

- ContactForm: every field has a visible `<label>`, `aria-invalid` flips on
  error, `aria-describedby` points at inline error text, the submit
  `<button>` is disabled during submit (with text changing to "sending…"),
  and the success state is announced via `aria-live="polite"`
- Honeypot field is `position: absolute; left: -10000px` (off-screen but
  still in the layout) so screen readers don't see it and bots that
  enumerate inputs do

## Deferred to v2

- Automated axe-core in CI (Playwright + `@axe-core/playwright`) — would
  catch regressions; currently a manual pass at deploy time
- Voice / TTS support for the terminal's typed output (decorative-only at v1)
- Full screen-reader transcript test on case-study markdown — relies on
  mdsvex output staying clean; spot-checked but not exhaustively walked
- Forced-colors mode tightening: HeroName has a `forced-colors` fallback;
  other gradient text and color-mix usages should be reviewed
